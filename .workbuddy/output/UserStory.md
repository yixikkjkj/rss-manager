## 1. 业务背景与价值

### 1.1 业务背景

- **当前业务现状（行业 / 产品 / 用户规模）**：用户当前使用浏览器插件 Feedbro 管理 RSS 订阅，已积累一份 4 分组 41 源的 OPML 订阅清单（2026-08-10 导出，见 material_digest D1）。订阅数据仅存于浏览器扩展、无服务端、无统一管理入口；用户规模为**个人单用户**（甲方决策者 = 最终用户 = 维护者，三角色合一）。
- **触发本次需求的事件（新场景 / 痛点修复）**：由"从零搭建一个 RSS 管理器"诉求驱动启动（用户原文："我们需要从零开始，搭建这样一个管理器"）。冷启动场景下，OPML 清单存在系统性数据质量问题（material_digest D1 逐条记录：http 明文 5 处、双斜杠 URL 1 处、xmlUrl/htmlUrl 域名不一致 4 处、缺 htmlUrl 4 源、text/title 不一致多处，41 源中受影响源 ≥ 14 个，占比 ≥ 34%）；同时订阅数据仅存浏览器、无备份、不可迁移（数据资产风险）。
- **本系统在产品矩阵中的位置**：rss-manager 是用户个人内容基础设施中的**独立自托管组件**，承担"订阅管理 + 阅读 + 检索"核心职责；对外无下游系统，移动端以响应式 Web 覆盖（经中间确认 U-02：不做移动 App 同步 API），形成"单实例自托管 + 浏览器多端访问"闭环。

### 1.3 方案收益与价值

| 项 | 说明 |
| --- | --- |
| 功能模块 | OPML 导入、分组/源管理、定时抓取、源健康、阅读/已读、收藏夹、全文搜索、OPML 导出、单用户登录、Readability 全文抓取（MVP F1–F14） |
| 预期价值收益 | 订阅冷启动从"手动逐源录入"降至"一次 OPML 导入"；新文章触达从"手动刷新"变为"定时自动抓取"；摘要源阅读内嵌全文无需跳出；失效源从"人工发现"变为"自动标记"；历史文章可全文检索；值得留存文章可按收藏夹归档；订阅数据从"仅存浏览器"变为"自有实例单文件可备份" |
| 量化标准 | 对齐高层架构 §1.3/§2.3 量化目标 V1–V4：41/41 源导入解析成功（100%）、≥39 源首抓成功（≥95%）、失效识别周期 ≤7 天、未读文章 ≤3 步读完、搜索响应 P95 ≤3 秒、全局默认与单源抓取间隔下限均 ≥30 分钟 |

### 1.4 术语清单

> 统一文档中专有名词的中英文对照与含义，与 system-architect 术语表对齐。

| 术语 | 英文 | 含义 |
| --- | --- | --- |
| OPML | Outline Processor Markup Language | 订阅清单交换格式，本系统导入/导出的标准格式（OPML 1.0） |
| 订阅源 / Feed | Feed | 一个可抓取的 RSS/Atom 内容源，由 xmlUrl 唯一标识 |
| 分组 | Folder / Category | 订阅源的一级归类（Blogs / 杂志资讯 / 计算机发展资讯 / 已失效） |
| 摘要源 | Partial-content feed | 只输出摘要、不输出完整正文的 Feed（如 36kr、部分 WordPress 站） |
| 全文抓取 | Readability / Full-content fetch | 对摘要源正文页抽取完整正文并内嵌展示的能力（readabilityrs） |
| 源健康 | Feed health | 订阅源抓取成功/失败状态与连续失败计数的监控能力 |
| 指数退避 | Exponential backoff | 连续抓取失败后，抓取间隔按指数增长的重试策略 |
| 收藏夹 | Folder | 用户自建的文章归档容器，一篇文章可归入多个收藏夹（F14） |
| FTS5 | SQLite Full-Text Search 5 | SQLite 内建全文搜索引擎，本系统搜索能力的底座 |
| WAL | Write-Ahead Logging | SQLite 写前日志模式，提升并发读写能力；备份 = 复制单文件 |
| 已读/未读 | Read/Unread | 文章阅读状态的二元标记，驱动未读计数与筛选 |
| 单用户 | Single-user | 系统仅服务一个用户账号，数据模型预留 user 维度（经中间确认 U-01） |
| WebSub | WebSub (PubSubHubbub) | 订阅源主动推送更新的协议（P2 功能 F16，MVP 不做） |

## 4. 角色与场景

### 4.1 角色清单

> 与高层架构 §2.1 核心角色关注点对齐。本项目为个人项目，甲方决策者、最终用户、维护者三重身份集中于用户本人；另设上游订阅源站点为受影响方。

| 角色 | 业务身份 | 主要操作 | 核心关注点 |
| --- | --- | --- | --- |
| 阅读者 | 用户本人（最终用户，日常阅读者） | 按分组浏览文章、阅读详情、标记已读、全文搜索、收藏到收藏夹、按收藏夹翻阅 | 41 源信息每天读得完：按分组高效浏览、未读不遗漏、摘要源内嵌全文、搜索能召回历史文章、值得留存文章可归档 |
| 决策者 | 用户本人（甲方决策者，项目 Owner） | 技术选型、验收、后续演进决策 | 数据自控与零订阅成本：订阅清单、阅读历史、搜索索引全部保存在自有实例，不依赖第三方 SaaS |
| 维护者 | 用户本人（自托管维护者） | 导入 OPML、管理订阅源、处置失效源、导出备份、登录与安全加固 | 单文件运维与安全基线：升级 = 替换单个二进制，备份 = 复制单个 SQLite 文件，公网暴露不被入侵，失效源可发现可处置 |
| 受影响方：订阅源站点 | 上游内容提供方（36kr、阮一峰、个人博客等 41 源） | 被动接收抓取请求 | 抓取频率礼貌：不被高频轮询触发封禁或限流（research_report R-01 反爬风险） |

> 硬指标自检：≥3 类角色（阅读者/决策者/维护者/受影响方 4 类）；每行含业务身份、主要操作、核心关注点；核心关注点为具体诉求，非笼统"使用方便"。未对高层架构定义的角色做子角色拆分（无"运营管理员/合规管理员"等新增细分），避免 §3 功能归属与下游模块边界漂移。

| S5 | 维护者 | 定期备份/迁移订阅 | 一键导出 OPML，保留分组结构，可被 Feedbro/FreshRSS 再导入 | 每月 1 次 |
| S6 | 维护者 | 公网部署，首次/日常登录 | 账号密码登录进入系统，未登录无法访问任何数据 | 每日 1 次 |
| S7 | 受影响方：源站点 | 系统调度器触发抓取 | 全局默认与单源抓取间隔均 ≥30 分钟，失败指数退避，不触发封禁 | 每源每 30~60 分钟 1 次 |
| S8 | 阅读者 | 阅读时想留存/归档某篇文章 | 收藏到收藏夹、按收藏夹翻阅、可创建/重命名/删除收藏夹、可取消收藏 | 每日 1~3 次 |

## 5. 用户旅程（UserStory）

> 说明：MVP 覆盖 F1–F14，共 11 条 US（维护者视角 6 条 + 阅读者视角 5 条）；P2 后续版本覆盖 F15–F18，共 4 条 US（US-11~US-14）。每条 US 按 5.x.1~5.x.7 七段式展开。UE 视觉稿由 Phase 5 细化，本节以交互路径与节点为主。
>
> **接口风格约定（经 G4 用户反馈，统一适用全部 US）**：系统对外（前端 → 后端）提供的所有 API 统一采用「HTTP POST + JSON body」，接口名显式指出功能（形如 `/api/rpc/{资源}_{动作}`，例如 `/api/rpc/article_mark_read`），不使用 REST path param（如 `/feeds/{id}`）、query param、form param；请求参数一律作为 JSON 字段置于请求体。系统出站抓取外部 Feed 源/正文页仍为 HTTP GET 拉取，属系统对外部内容的获取，非系统对外提供的 API 接口风格。

### 5.1 US-1：OPML 导入与数据质量规范化（F1）

#### 5.1.1 业务场景

- **视角**：维护者
- **描述逻辑**：用户首次部署 rss-manager 后，希望把历史积累的 Feedbro 订阅清单（4 分组 41 源的 OPML 文件）一次性迁入系统，并自动修正清单中存在的 http 明文、双斜杠 URL、缺失 htmlUrl、text/title 不一致等数据质量问题，确保冷启动后绝大多数源可直接抓取可用。

#### 5.1.2 业务流程

- **视角**：用户
- **描述方式**：
  - Given 用户已登录并进入"导入/导出"页，且手头有一份 Feedbro 导出的 OPML 文件，
  - When 用户选择文件并点击"导入"，
  - Then 系统解析 OPML 1.0、执行数据质量规范化流水线，并展示逐源导入报告（含每源规范化改动与最终 URL），用户确认后写入订阅库并触发首抓。

#### 5.1.3 UE 原型

- 核心路径：导入/导出页 → 文件上传控件（拖拽或点击选择）→ 点击"导入"→ 加载态（解析中）→ 导入报告表格（逐源列出：显示名 / 原 xmlUrl / 规范化后 xmlUrl / 改动类型 / 状态）→ 用户点击"确认导入"→ 跳转源管理页。
- 关键节点：导入报告为强制确认环节，规范化改动（http 升级、双斜杠修复、text 命名、域名不一致提示）逐条以图标 + 文字标出，用户可一键"全部采纳"或逐条调整。

#### 5.1.4 业务逻辑

- **视角**：业务系统
- **描述方式**：系统解析 OPML outline 树 → 识别 4 个一级分组与 41 个 type="rss" 源 → 对每源执行规范化：① URL 双斜杠归一；② http xmlUrl/htmlUrl 尝试升级 https（升级成功写入 https，失败保留原值并标记）；③ 以 text 作为显示名（text 缺失时回退 title）；④ 缺 htmlUrl 时以 xmlUrl 兜底并标记；⑤ xmlUrl 与 htmlUrl 域名不一致时提示；⑥ 以 xmlUrl 为唯一键做同站多源并存（去重仅针对完全相同的 xmlUrl）→ 生成导入报告 → 用户确认后事务化写入分组与源表 → 触发逐源首抓。

#### 5.1.5 数据描述

- 核心数据流转：OPML 文件（head/title + outline 分组 + outline 源）→ 内存规范化中间态（原值 + 改动类型 + 新值）→ 导入报告视图 → 分组表（group）+ 源表（feed：text、xmlUrl、htmlUrl、group_id、http 升级标记）→ 首抓任务入队。
- 关键字段：`text`（显示名）、`title`（Feed 原始标题）、`xmlUrl`（唯一键）、`htmlUrl`（原文跳转）、`group`（分组归属）、规范化改动标记（upgraded_to_https / slash_normalized / html_url_missing / domain_mismatch）。

#### 5.1.6 验收标准 AC

- Given 用户上传含 4 分组 41 源的 OPML 1.0 文件，When 点击导入，Then 系统解析全部 41 源并进入规范化流水线，41/41 源解析成功（成功率 100%）。
- Given 源 xmlUrl 为 http 明文（如 http://feeds.feedburner.com/PythonInsider），When 执行规范化，Then 系统尝试升级为 https 并验证；升级成功则写入 https，升级失败则保留原 http 并在导入报告标注。
- Given 源 xmlUrl 含双斜杠（如 https://hustyichi.github.io//feed），When 执行规范化，Then 系统将双斜杠归一为单斜杠并在报告标注。
- Given 源 text 与 title 不一致（如 text="李璐慧blog" title="Luhui's Personal Website"），When 执行规范化，Then 以 text 作为显示名，title 作为元数据保留。
- Given 某源缺失 htmlUrl，When 执行规范化，Then 以 xmlUrl 兜底并标注缺失，不阻断导入。
- Given 用户点击"确认导入"，When 系统写入订阅库，Then 全部 41 源完成首抓，≥39 源首抓成功（≥95%），首抓失败源在源健康面板可见。
- Given 导入文件格式非法（非 OPML / 空文件 / 无 outline），When 用户点击导入，Then 系统给出明确错误提示并中止导入，不写入任何脏数据。

#### 5.1.7 外部集成接口

- 系统接口（前端 ↔ 后端，统一 HTTP POST + JSON body，接口名显式指出功能）：`/api/rpc/opml_import`（上传导入，OPML 内容作为 JSON 字段随请求体传入）、`/api/rpc/opml_import_report`（查询导入报告）。
- 依赖外部能力：Feedbro 导出的 OPML 文件内容（同步解析）；首抓依赖 41 个外部 Feed 源（出站 HTTP GET 拉取，异步）与 feed-rs 解析引擎（进程内库调用）。规范化中 http→https 升级验证需对外发起 HTTPS 探测请求。

### 5.2 US-2：订阅源与分组管理（F2、F3）

#### 5.2.1 业务场景

- **视角**：维护者
- **描述逻辑**：导入后用户需要长期维护订阅结构——新增/编辑/删除分组、手动添加新的订阅源、修改源的 xmlUrl/htmlUrl/显示名、调整源所属分组，保持订阅清单与个人阅读兴趣同步。

#### 5.2.2 业务流程

- **视角**：用户
- **描述方式**：
  - Given 用户进入源管理页，
  - When 用户点击"添加源"并填写 xmlUrl（必填）、显示名、所属分组后保存，
  - Then 系统校验 URL 并测试抓取，成功后新增源并归入指定分组；编辑/删除/分组调整操作即时生效并反映到订阅列表侧边栏。

#### 5.2.3 UE 原型

- 核心路径：源管理页 → 表格展示（显示名 / xmlUrl / htmlUrl / 状态）→ 顶部"添加源"按钮 → 弹窗表单（xmlUrl 必填、显示名、分组下拉）→ "测试抓取"按钮 → 保存 → 表格刷新。
- 关键节点：编辑弹窗与添加弹窗复用同一表单；删除为二次确认；源状态列展示"正常 / 失败中 / 已失效"三态。

#### 5.2.4 业务逻辑

- **视角**：业务系统
- **描述方式**：系统对新增/编辑的 xmlUrl 做格式校验与可达性测试抓取 → 测试成功则写入/更新源记录（feed 表），测试失败返回具体错误（超时/HTTP 状态/解析失败）且不阻断保存但标记"待验证" → 分组增删改校验（删除分组需先清空或迁移其下源）→ 源分组归属调整更新 feed.group_id → 变更后刷新订阅列表未读计数。

#### 5.2.5 数据描述

- 核心数据流转：源管理表单输入 → 校验 + 测试抓取 → feed 表增删改 → group 表增删改 → 订阅列表侧边栏（分组 + 未读计数）刷新。
- 关键字段：`xmlUrl`（唯一键）、`htmlUrl`、`text`（显示名）、`group_id`、`status`（正常/失败中/已失效）、`last_fetched_at`、`consecutive_failures`。

#### 5.2.6 验收标准 AC

- Given 用户添加一个新源并填写有效 xmlUrl，When 点击保存，Then 系统测试抓取成功后写入该源并归入所选分组，订阅列表侧边栏出现该源。
- Given 用户添加源时 xmlUrl 不可达或格式非法，When 点击保存，Then 系统返回具体错误（DNS/超时/HTTP 状态/解析失败）并保留表单输入，不写入脏数据。
- Given 用户编辑某源显示名或 htmlUrl，When 保存，Then 源列表即时更新且不影响该源已抓取文章与未读计数。
- Given 用户删除某分组且该分组下仍有源，When 确认删除，Then 系统提示需先迁移源或级联删除，避免源成为无主数据。
- Given 用户删除某源，When 确认删除，Then 该源及其未读计数从订阅列表移除，其历史文章保留可检索（软删除或保留文章）。
- Given 用户将某源从分组 A 调整到分组 B，When 保存，Then 该源未读计数计入分组 B，分组 A 未读计数相应扣减。

#### 5.2.7 外部集成接口

- 系统接口（前端 ↔ 后端，统一 HTTP POST + JSON body，接口名显式指出功能）：`/api/rpc/group_create`、`/api/rpc/group_update`、`/api/rpc/group_delete`、`/api/rpc/feed_create`、`/api/rpc/feed_update`、`/api/rpc/feed_delete`、`/api/rpc/feed_test`。
- 依赖外部能力：新增/编辑源的"测试抓取"依赖目标源站点（出站 HTTP GET 拉取）与 feed-rs 解析引擎（进程内库调用）；不依赖第三方 API。

### 5.3 US-3：定时抓取配置与抓取日志（F4）

#### 5.3.1 业务场景

- **视角**：维护者
- **描述逻辑**：导入完成后，用户希望系统按可配置的间隔自动抓取各源新文章（礼貌抓取、不触发封禁）；每个订阅源可单独设置抓取间隔并覆盖全局默认，全局默认与单源下限均不低于 30 分钟。用户还能查看最近抓取任务的执行明细与错误，以判断系统是否正常持续更新。

#### 5.3.2 业务流程

- **视角**：用户
- **描述方式**：
  - Given 用户进入设置页，
  - When 用户配置全局默认抓取间隔（或为某个订阅源单独设置抓取间隔覆盖全局默认）并保存，
  - Then 系统按「该源覆盖值，未覆盖则用全局默认」调度抓取，且全局默认与任一单源实际间隔均不低于 30 分钟；用户可在抓取日志页按源/时间筛选查看每次抓取结果与错误详情。

#### 5.3.3 UE 原型

- 核心路径：设置页 → 全局默认抓取间隔输入（分钟，最小 30）→ 单源间隔覆盖入口（在源管理页或设置页对某源单独设置间隔）→ 保存 → 抓取日志页查看明细（源 / 时间 / 结果 / 错误详情）。
- 关键节点：抓取日志表格按时间倒序，错误详情展开显示"超时 / HTTP 状态 / 解析失败"三类原因；间隔配置对低于 30 分钟的值给出提示或强制下限（全局默认与单源覆盖均受 30 分钟下限约束）。

#### 5.3.4 业务逻辑

- **视角**：业务系统
- **描述方式**：进程内调度器按每源独立间隔触发抓取 → 单源实际间隔 = max(该源覆盖值（feed.fetch_interval，未设置则继承全局默认）, 30 分钟)（礼貌性下限，全局默认与单源覆盖值本身亦不得低于 30 分钟）→ 对每源发起 HTTP GET（请求超时 ≤30 秒）→ feed-rs 解析 → 新文章（按文章 guid/链接去重）入文章表 → 抓取成功重置连续失败计数并恢复该源间隔；抓取失败（超时/HTTP 错误/解析失败）进入指数退避并累计连续失败计数 → 每次抓取结果写抓取日志。

#### 5.3.5 数据描述

- 核心数据流转：调度器 → HTTP GET（Feed 原始内容）→ feed-rs 解析为统一模型 → 文章表（article：title、content、link、published_at、feed_id）新增/去重 → 抓取日志表（fetch_log：feed_id、started_at、status、error_type、duration_ms）。
- 关键字段：`feed.fetch_interval`（单源覆盖值，NULL 表示继承全局默认）、全局默认间隔（系统配置）、`timeout_ms`（≤30000）、`consecutive_failures`、`last_fetched_at`、`backoff_until`（退避截止时间）。

#### 5.3.6 验收标准 AC

- Given 用户设置全局默认抓取间隔为 60 分钟，When 保存，Then 系统按约 60 分钟间隔触发抓取，且任何单源实际间隔不低于 30 分钟。
- Given 用户为某源单独设置抓取间隔为 120 分钟，When 保存，Then 该源按约 120 分钟间隔抓取，其余未设置覆盖值的源按全局默认（60 分钟）抓取。
- Given 用户尝试设置全局默认或单源覆盖间隔为 15 分钟，When 保存，Then 系统拒绝或提示最低 30 分钟下限（礼貌抓取约束）。
- Given 某源正常返回 Feed，When 抓取执行，Then 新文章按 guid/链接去重后入库，不产生重复文章。
- Given 某源单次抓取超时（超过 30 秒）或返回 5xx，When 抓取执行，Then 系统记录错误类型并累计连续失败计数，触发指数退避。
- Given 用户打开抓取日志页，When 按某源/时间筛选，Then 系统展示该源最近抓取记录及错误详情（超时/HTTP 状态/解析失败）。
- Given 抓取间隔运行 7 天，When 期间持续抓取，Then 调度器不崩溃、无内存泄漏、错误被记录而非静默丢失。

#### 5.3.7 外部集成接口

- 系统接口（前端 ↔ 后端，统一 HTTP POST + JSON body，接口名显式指出功能）：`/api/rpc/fetch_config_update`（设置全局默认间隔与单源覆盖间隔）、`/api/rpc/fetch_log_list`（抓取日志查询）、`/api/rpc/fetch_now`（手动触发抓取）。
- 依赖外部能力：41 个外部 Feed 源（出站 HTTP GET 拉取，异步，reqwest）；feed-rs 解析引擎（进程内库调用）。不依赖第三方调度服务。

### 5.4 US-4：源健康监控与失效源处置（F5）

#### 5.4.1 业务场景

- **视角**：维护者
- **描述逻辑**：用户希望系统能自动识别长期无法抓取的失效源（如已失效的 linux.cn），避免内容断供却无人知晓；识别后用户可重试、修复 URL 或删除该源。

#### 5.4.2 业务流程

- **视角**：用户
- **描述方式**：
  - Given 某源连续 3 次抓取失败（HTTP 错误/解析失败/超时），
  - When 系统累计失败计数达到阈值，
  - Then 系统将该源标记为"已失效"并隔离展示（红色标识/失效分组），用户在源健康监控页看到失效源及错误原因，可一键重试、修复 URL 或删除。

#### 5.4.3 UE 原型

- 核心路径：源健康监控页 → 全量源状态总览（正常/失败中/已失效 + 连续失败次数 + 最近抓取时间）→ 失效源高亮红色 → 单源操作（重试 / 编辑 URL / 删除）。
- 关键节点：失效源在订阅列表侧边栏以红色标识区分，其未读计数不参与正常未读统计（失效隔离）。

#### 5.4.4 业务逻辑

- **视角**：业务系统
- **描述方式**：系统维护每源连续失败计数 → 单次抓取成功重置为 0，单次失败 +1 → 计数达到 3 时触发失效标记并进入隔离态 → 隔离态源暂停常规抓取（仅保留低频探测或手动重试）→ 用户重试成功则解除失效标记并恢复计数；用户修复 URL 后重新测试抓取成功则解除。

#### 5.4.5 数据描述

- 核心数据流转：抓取结果 → 连续失败计数更新 → 源健康状态（正常/失败中/已失效）→ 源健康监控页视图 → 用户处置动作（重试/编辑/删除）→ 状态回写。
- 关键字段：`consecutive_failures`（阈值 3）、`status`（healthy/failing/dead）、`last_error`（错误类型与详情）、`isolated_at`（隔离时间）。

#### 5.4.6 验收标准 AC

- Given 某源连续 3 次抓取失败，When 失败计数达到 3，Then 系统自动将其标记为"已失效"并隔离展示，识别周期（从首次失败到标记）≤7 天。
- Given 某源单次抓取成功后，When 再次抓取，Then 连续失败计数重置为 0，不误判为失效。
- Given 某源被标记失效，When 用户点击"重试"且抓取成功，Then 系统解除失效标记并恢复常规抓取。
- Given 某源被标记失效，When 用户在源健康面板查看，Then 可见连续失败次数、最近抓取时间与具体错误原因（超时/HTTP 状态/解析失败）。
- Given 失效源处于隔离态，When 订阅列表展示未读计数，Then 失效源文章不计入正常分组未读计数。

#### 5.4.7 外部集成接口

- 系统接口（前端 ↔ 后端，统一 HTTP POST + JSON body，接口名显式指出功能）：`/api/rpc/health_overview`（全量源健康总览）、`/api/rpc/feed_retry`（重试失效源）。

#### 5.5.6 验收标准 AC

#### 5.6.1 业务场景

- **视角**：维护者

#### 5.6.2 业务流程

- **视角**：用户
- **描述方式**：
  - Given 用户访问系统任意页面且未登录，

  - Then 系统重定向到登录页；用户输入账号密码登录成功后进入系统，会话保持；登出后会话失效。

#### 5.6.3 UE 原型

- 核心路径：任意受保护页面 → 登录页（账号 + 密码）→ 登录成功 → 系统首页（文章列表）；右上角"登出"按钮。
- 关键节点：首次部署需完成初始密码设置；密码输入框支持显隐切换；连续登录失败给出限流提示。

#### 5.6.4 业务逻辑

- **视角**：业务系统
- **描述方式**：系统在首次启动时读取/生成单用户凭据（账号 + 初始密码，经环境变量或首次设置向导配置）→ 登录请求校验凭据（密码以 argon2id 加盐哈希存储比对）→ 成功则签发会话（HttpOnly + Secure Cookie）→ 所有受保护接口校验会话 → 登录失败限流（连续失败锁定/退避）→ 登出销毁会话 → 数据模型预留 user 维度（users 表，当前单用户）。

#### 5.6.5 数据描述

- 核心数据流转：登录表单 → 凭据校验 → 会话 Cookie 签发 → 受保护接口鉴权 → 登出销毁。
- 关键字段：`username`、`password_hash`（加盐哈希，不存明文）、`session_token`/会话过期时间、`failed_attempts`/`locked_until`（限流）。

#### 5.6.6 验收标准 AC

- Given 用户未登录，When 访问文章列表/搜索/导出等任意受保护页面，Then 系统重定向到登录页，不泄露任何订阅数据。
- Given 用户输入正确账号密码，When 提交登录，Then 系统签发会话并进入系统首页。
- Given 用户输入错误密码，When 连续失败达到阈值（如 5 次），Then 系统触发限流/锁定并给出提示。
- Given 用户点击登出，When 会话销毁，Then 再次访问受保护页面需重新登录。
- Given 用户设置新密码，When 提交，Then 密码强度满足 12 位以上且含大小写字母 + 数字 + 特殊字符，否则拒绝并提示。
- Given 会话在浏览器中保持，When 会话未过期，Then 用户刷新页面无需重复登录。

#### 5.6.7 外部集成接口

- 系统接口（前端 ↔ 后端，统一 HTTP POST + JSON body，接口名显式指出功能）：`/api/rpc/auth_login`、`/api/rpc/auth_logout`、`/api/rpc/auth_change_password`。
- 依赖外部能力：无（认证授权为系统内建能力，不依赖第三方 SSO/OAuth；单用户形态下无需外部身份提供方）。

#### 5.8.3 UE 原型

#### 5.8.4 业务逻辑

- **视角**：业务系统
- **描述方式**：系统按 feed_id 判定该源是否启用全文抓取开关 → 启用且正文为摘要时调用 readabilityrs 抽取正文并缓存 → 抽取成功则内嵌展示全文；抽取失败（网络/解析/超时）则降级展示 Feed 原始摘要 + "原文跳转"按钮 → 打开详情自动将 is_read 置为 true → "原文跳转"在新窗口打开 htmlUrl（浏览器侧）。

#### 5.8.5 数据描述

- 核心数据流转：文章表（标题/摘要正文/链接/时间）→ 全文抓取（readabilityrs 对 htmlUrl 抽取）→ 全文缓存（full_content 字段）→ 详情视图（内嵌全文或降级摘要 + 跳转按钮）。

#### 5.8.6 验收标准 AC

- Given 摘要源文章（如 36kr），When 用户打开详情，Then 系统内嵌展示 Readability 抽取的完整正文，无需跳出阅读器。
- Given 某源全文抓取失败（网络/解析/超时），When 用户打开详情，Then 系统降级展示 Feed 摘要正文并提供"原文跳转"按钮。
- Given 用户点击"原文跳转"，When 触发跳转，Then 系统在新窗口打开该文章 htmlUrl，全程 ≤1 次点击。
- Given 用户打开详情，When 渲染完成，Then 该文章 is_read 自动置为已读（点击即读/打开即读）。
- Given 用户在详情页使用 j/k 键，When 按下，Then 切换到上一篇/下一篇；按 m 键切换已读/未读。
- Given 对 41 源做全文抓取冒烟测试，When 逐源执行，Then 摘要源可正常内嵌或明确降级跳转，不出现空白正文或崩溃。

#### 5.8.7 外部集成接口

- 系统接口（前端 ↔ 后端，统一 HTTP POST + JSON body，接口名显式指出功能）：`/api/rpc/article_detail`（文章详情）、`/api/rpc/article_fetch_full_content`（触发 Readability 全文抓取）。
- 依赖外部能力：Readability 全文抓取依赖 readabilityrs（进程内库调用）并对源站正文页发起出站 HTTP GET；原文跳转依赖浏览器打开 htmlUrl（浏览器侧行为，非系统 API）。全文抓取失败降级为本地摘要展示，不依赖第三方内容服务。

- Given 搜索结果，When 用户点击某条，Then 进入对应文章详情并自动标记已读。

#### 5.10.7 外部集成接口

- 系统接口（前端 ↔ 后端，统一 HTTP POST + JSON body，接口名显式指出功能）：`/api/rpc/search`（全文搜索，关键词作为 JSON 字段传入）。
- 依赖外部能力：SQLite FTS5（内建，进程内库调用）；无独立搜索引擎或第三方搜索服务。

### 5.11 US-11：过滤规则（F15，P2 后续版本）

#### 5.11.1 业务场景

- **视角**：阅读者/维护者
- **描述逻辑**：订阅增长后，用户希望用"条件（来源/关键词/标签）→ 动作（标记已读/忽略/归组）"的规则自动过滤低价值内容，降低阅读噪音。

#### 5.11.2 业务流程

- **视角**：用户
- **描述方式**：
  - Given 用户进入过滤规则页，
  - When 用户新建一条规则并保存，
  - Then 后续抓取入库的新文章自动按规则执行动作（标记/忽略/归组）。

#### 5.11.3 UE 原型

- 核心路径：过滤规则页 → 规则列表 → "新建规则"（条件选择 + 动作选择）→ 保存 → 规则生效。
- 关键节点：条件为"来源/关键词/标签"，动作为"标记已读/忽略/归组"；规则可启用/停用。

#### 5.11.4 业务逻辑

- **视角**：业务系统
- **描述方式**：系统维护规则表 → 抓取入库时对每条文章匹配启用中的规则 → 命中则执行对应动作（置已读/打忽略标记/调整分组）→ 规则优先级按创建顺序。

#### 5.11.5 数据描述

- 核心数据流转：规则配置 → 文章入库 → 规则匹配 → 动作执行（is_read/ignore_flag/group_id）。
- 关键字段：`rule`（条件 + 动作 + 状态）、`match_field`（feed_id/keyword/tag）、`action`。

#### 5.11.6 验收标准 AC

- Given 用户新建"来源=X 且关键词=Y → 忽略"规则，When 新文章入库且命中，Then 该文章被忽略，不出现在未读列表。
- Given 用户停用某规则，When 新文章入库，Then 该规则不再生效。
- Given 规则引擎运行，When 41 源规模下批量匹配，Then 不阻塞抓取入库流程，性能开销可忽略。

#### 5.11.7 外部集成接口

- 系统接口（前端 ↔ 后端，统一 HTTP POST + JSON body，接口名显式指出功能）：`/api/rpc/filter_rule_create`、`/api/rpc/filter_rule_update`、`/api/rpc/filter_rule_delete`、`/api/rpc/filter_rule_toggle`。
- 依赖外部能力：无（规则匹配为本地逻辑）。

### 5.12 US-12：WebSub 实时推送（F16，P2 后续版本）

#### 5.12.1 业务场景

- **视角**：阅读者
- **描述逻辑**：对支持 WebSub 的源，用户希望新文章发布后近实时推送（≤1 分钟），无需等待下一轮轮询。

#### 5.12.2 业务流程

- **视角**：用户
- **描述方式**：
  - Given 某源支持 WebSub，
  - When 系统订阅该源 hub，
  - Then 源站新文章发布后系统近实时收到推送并入库，用户几乎即时可见。

#### 5.12.3 UE 原型

- 核心路径：源管理页标注 WebSub 状态 → 支持源自动订阅 hub → 新文章实时出现。
- 关键节点：不支持 WebSub 的源保留轮询兜底，用户无感知差异。

#### 5.12.4 业务逻辑

- **视角**：业务系统
- **描述方式**：系统探测源是否声明 hub → 声明则向 hub 发起订阅（回调端点）→ 收到推送验证签名后解析入库 → 推送失败/未声明则回退轮询。

#### 5.12.5 数据描述

- 核心数据流转：hub 订阅 → 回调推送 → 签名验证 → 文章入库。
- 关键字段：`hub_url`、`web_sub_status`、`callback_secret`。

#### 5.12.6 验收标准 AC

- Given 某源支持 WebSub，When 系统订阅 hub 后源发布新文章，Then 新文章端到端延迟 ≤1 分钟。
- Given 某源不支持 WebSub 或推送失败，When 触发，Then 系统回退轮询兜底，不漏文章。

#### 5.12.7 外部集成接口

- 系统接口（前端 ↔ 后端，统一 HTTP POST + JSON body，接口名显式指出功能）：`/api/rpc/websub_subscribe`（订阅源 hub）、`/api/rpc/websub_callback`（接收 hub 推送回调）。
- 依赖外部能力：源站 WebSub hub（订阅/回调，HTTPS）；回调需公网可达端点。

### 5.13 US-13：发布频率统计（F17，P2 后续版本）

#### 5.13.1 业务场景

- **视角**：维护者

#### 5.13.2 业务流程

- **视角**：用户
- **描述方式**：
  - Given 用户进入趋势/频率页，
  - When 用户按源查看近 30 天发布频率，
  - Then 系统展示逐源发布频率并可排序，辅助识别低质/失效源。

#### 5.13.3 UE 原型

- 核心路径：趋势/频率页 → 逐源近 30 天发布频率列表（可排序）→ 识别停更/异常源。
- 关键节点：按发布频率降序/升序排序，标注停更源。

#### 5.13.4 业务逻辑

- **视角**：业务系统
- **描述方式**：系统按 feed_id 聚合近 30 天文章数 → 计算日均发布频率 → 排序展示 → 标记连续无发布源。

#### 5.13.5 数据描述

- 核心数据流转：文章表按 feed_id + published_at 聚合 → 频率统计视图。
- 关键字段：`feed_id`、`post_count_30d`、`daily_avg`、`last_post_at`。

#### 5.13.6 验收标准 AC

- Given 用户查看趋势/频率页，When 加载，Then 展示每源近 30 天文章数与日均频率，可排序。
- Given 某源 30 天无新文章，When 展示，Then 该源被标注为停更/低质候选。

#### 5.13.7 外部集成接口

- 系统接口（前端 ↔ 后端，统一 HTTP POST + JSON body，接口名显式指出功能）：`/api/rpc/feed_frequency_stats`（逐源近 30 天发布频率）。
- 依赖外部能力：无（基于本地文章表聚合）。

### 5.14 US-14：自动 OPML 备份（F18，P2 后续版本）

#### 5.14.1 业务场景

- **视角**：维护者
- **描述逻辑**：用户希望系统按周期自动把订阅清单备份为 OPML 文件存到服务器本地目录，避免遗忘手动备份导致订阅资产丢失。

#### 5.14.2 业务流程

- **视角**：用户
- **描述方式**：
  - Given 用户配置自动备份周期，
  - When 到达备份时间点，
  - Then 系统自动导出 OPML 到服务器本地目录，并保留最近 N 份备份。

#### 5.14.3 UE 原型

- 核心路径：设置页配置自动备份周期与保留份数 → 系统按周期执行 → 数据备份页可见备份清单。
- 关键节点：备份文件本地落盘，保留最近 N 份，超出滚动清理。

#### 5.14.4 业务逻辑

- **视角**：业务系统
- **描述方式**：系统按周期触发 OPML 序列化 → 写入本地备份目录（带时间戳文件名）→ 滚动保留最近 N 份 → 备份结果可在备份页查看。

#### 5.14.5 数据描述

- 核心数据流转：分组表 + 源表 → 周期导出 → 本地 .opml 文件 → 备份清单。
- 关键字段：备份文件名、时间戳、保留份数 N。

#### 5.14.6 验收标准 AC

- Given 用户配置每日备份且保留 7 份，When 到达备份时间点，Then 系统生成当日 OPML 备份文件并清理第 8 份及更早备份。
- Given 自动备份执行失败，When 触发，Then 系统记录错误并在备份页可见，不影响主流程。

#### 5.14.7 外部集成接口

- 系统接口（前端 ↔ 后端，统一 HTTP POST + JSON body，接口名显式指出功能）：`/api/rpc/backup_config_update`（备份周期与保留份数）、`/api/rpc/backup_list`（备份清单）。
- 依赖外部能力：无（本地文件写盘）。

### 5.15 US-15：收藏夹（F14，MVP）

#### 5.15.1 业务场景

- **视角**：阅读者
- **描述逻辑**：用户在阅读过程中，希望把值得留存或稍后精读的文章归档到自定义收藏夹，避免淹没在每日信息流中；收藏夹支持创建/重命名/删除，文章可收藏/取消收藏，并可按收藏夹翻阅（一个收藏夹可含多篇文章，一篇文章可归入多个收藏夹）。不做收藏夹内排序/嵌套等高级能力（对齐 F14 边界）。

#### 5.15.2 业务流程

- **视角**：用户
- **描述方式**：
  - Given 用户在文章详情页（或列表操作入口），
  - When 用户点击"收藏"并选择一个收藏夹（可新建），
  - Then 系统将该文章加入该收藏夹并即时反馈；用户可进入收藏夹页按夹翻阅、重命名/删除收藏夹，或取消收藏。

#### 5.15.3 UE 原型

- 核心路径：文章详情页"收藏"按钮 → 收藏夹选择器（已有收藏夹列表 + "新建收藏夹"）→ 收藏成功提示 → 收藏夹页（收藏夹列表 + 各夹文章数）→ 点击某夹进入该夹文章流 → 取消收藏。
- 关键节点：收藏夹页支持创建/重命名/删除；删除收藏夹前二次确认（文章本身不删除，仅解除归档关系）；文章详情页可再次点击取消收藏。

#### 5.15.4 业务逻辑

- **视角**：业务系统
- **描述方式**：系统维护收藏夹表（folder）与文章-收藏夹关联表（article_folder）→ 收藏动作 = 在关联表插入（user_id + folder_id + article_id）唯一记录，取消收藏 = 删除该关联记录 → 创建/重命名/删除收藏夹校验（同用户内名称唯一、删除时解除其下全部关联但不删文章）→ 按收藏夹翻阅 = 按 folder_id 关联查询文章列表并按发布时间倒序返回 → 收藏夹内不做排序/嵌套（对齐 F14 边界）。

#### 5.15.5 数据描述

- 核心数据流转：收藏动作 → 收藏夹表（folder：id、name、user_id）+ 文章-收藏夹关联表（article_folder：folder_id、article_id）→ 收藏夹页（夹列表 + 各夹文章数）→ 按夹文章流。
- 关键字段：`folder.name`（收藏夹名，同用户内唯一）、`article_folder`（收藏夹↔文章多对多关联，user+folder+article 唯一防重复收藏）、`article_id`（关联文章）。

#### 5.15.6 验收标准 AC

- Given 用户在文章详情页点击"收藏"并选择收藏夹 A，When 确认，Then 该文章加入收藏夹 A，详情页收藏态即时更新。
- Given 用户收藏时收藏夹列表为空，When 点击"新建收藏夹"并输入名称，Then 系统创建收藏夹并将文章收藏入该夹。
- Given 用户对已收藏文章再次点击取消收藏，When 确认，Then 该文章从收藏夹移除，收藏态更新（不删除文章本身）。
- Given 用户重命名收藏夹，When 保存，Then 收藏夹名即时更新，关联文章不变。
- Given 用户删除某收藏夹，When 二次确认，Then 该收藏夹删除且其下关联全部解除，文章本身保留可读。
- Given 用户进入收藏夹页并点击某收藏夹，When 加载，Then 展示该夹下收藏文章列表（按发布时间倒序），一篇文章可同时出现在多个收藏夹。
- Given 用户未登录，When 访问收藏夹相关接口，Then 系统拒绝访问（401），不泄露收藏数据。

#### 5.15.7 外部集成接口

- 系统接口（前端 ↔ 后端，统一 HTTP POST + JSON body，接口名显式指出功能）：`/api/rpc/folder_create`、`/api/rpc/folder_rename`、`/api/rpc/folder_delete`、`/api/rpc/folder_list`、`/api/rpc/folder_article_list`、`/api/rpc/article_favorite`、`/api/rpc/article_unfavorite`。
- 依赖外部能力：无（收藏夹为本地数据关系，不依赖第三方服务）。

## 6. 非功能性需求

### 6.1 易用性需求

- **操作便利性**：阅读核心路径（列表 → 打开详情 → 标记已读）≤3 步；摘要源内嵌全文无跳转；全文抓取失败源降级"原文跳转"≤1 次点击（对齐 V3）；收藏/按收藏夹翻阅在详情页与收藏夹页内完成，不跳出主阅读流。
- **键盘快捷键**：详情页支持 j/k（上/下篇）、m（标记已读）快捷键，提升连续阅读效率。
- **UI 一致性**：全站统一使用分组侧边栏 + 列表 + 详情三段式布局；失效源/未读/错误状态使用统一视觉标识（红色失效、未读加粗、角标计数）；收藏夹操作使用统一"收藏/取消收藏"图标与状态反馈。
- **引导提示**：首次部署提供导入引导（上传 OPML → 查看导入报告 → 进入阅读）；新增源提供"测试抓取"反馈；搜索空结果、导入失败、抓取失败均给出明确提示。
- **错误反馈**：所有异常路径（导入非法文件、源不可达、登录失败、全文抓取失败）均给出可理解的错误信息，不含内部堆栈。
- **无障碍支持**：页面使用语义化 HTML，关键交互可键盘操作，正文与背景对比度满足可读性要求。

### 6.3 操作与环境需求

- **浏览器兼容性**：支持现代浏览器最近两个大版本（Chrome / Edge / Firefox / Safari）；响应式布局适配移动端浏览器（宽度 ≤480px 下侧边栏折叠为抽屉）。
- **网络环境**：自托管于局域网或公网，公网暴露时经 HTTPS 访问；抓取调度需能访问外部 Feed 源（HTTPS/HTTP）。
- **设备规格**：低配 VPS 或家庭服务器（≥512MB 内存、1 vCPU）；部署形态为单一可执行文件或单容器（Docker）。
- **运行环境**：Rust 编译单二进制；SQLite 单文件数据存储（WAL 模式）；前端构建产物经 rust-embed 编译期嵌入；支持 Linux/macOS/Windows 运行（Docker 或原生二进制）。
- **运行约束**：备份 = 复制 SQLite 单文件；升级 = 替换单个二进制；抓取调度为进程内调度，不依赖外部任务队列。

### 6.4 安全性需求

> 满足相关安全标准；部署与安全设计的详细策略由 Phase 5 的 security-architect / platform-architect 承接，本节给出产品侧安全需求基线。

#### 6.4.1 安全密码设置

- 系统账号密码设置支持达到以下强度：**12 位以上大小写字母 + 数字 + 特殊字符**；密码以 argon2id 加盐哈希存储，不存明文。

#### 6.4.2 安全软件架构

- 保证自身结构中各模块的通信安全（前端经 HTTPS 访问后端 API，接口统一 HTTP POST + JSON body、显式功能名，见 §5 接口风格约定）。
- 保证组件、用户、资源的认证与访问控制（所有受保护接口校验会话）。
- 与外部 Feed 源交互时，限制未经许可的接口访问（全局默认与单源抓取间隔、请求超时、失败退避）；对 http 明文源按安全基线处理；限制外部源可获取的内容范围（仅返回抓取请求所必需的元数据）；使用 HTTPS 等安全通讯协议。

#### 6.4.3 安全设计

- 提供认证授权功能：单用户账号密码登录 + 会话管理（Cookie HttpOnly + Secure），未登录拒绝访问全部数据接口。

#### 6.4.4 安全开发

- 对函数入口参数的合法性和准确性进行检查（导入文件、xmlUrl、搜索关键词、收藏夹名称等入口校验）。
- 进行输入边界检查，限制输入的正确长度和格式（URL 格式、OPML 结构、搜索词长度、收藏夹名称长度）。
- 保证不因代码编写导致可被直接利用的高危漏洞（SQL 注入、XSS、SSRF 抓取等）。
- 在输入输出模块中进行适当过滤，防范恶意指令与内部信息泄露（文章正文渲染做 XSS 转义/净化，错误信息不外泄堆栈）。
- 禁止使用未经授权和验证的代码（依赖锁定版本并跟踪演进）。
- 保证应用程序不存在任何可绕行安全机制的行为或遗留后门。

#### 6.4.5 安全测试和部署

- 进行安全扫描测试（依赖漏洞扫描 + 静态分析）。
- 进行安全配置基线检查（HTTPS、会话 Cookie 属性、密码强度）。
- 进行安全功能的测试（登录/登出/鉴权/限流）。
- 系统在上线前不存在高危风险（SSRF 抓取、存储型 XSS 等 OWASP 高危项清零）。

#### 6.4.6 数据安全

- **数据存储和传输加密**：在用户密码、身份鉴别信息等重要数据的存储（加盐哈希）、传输（HTTPS）过程进行适当加密，保障信息不被泄露；订阅与阅读数据存储于 SQLite 单文件，通过文件系统权限限制访问。
