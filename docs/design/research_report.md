### 2.1 行业标杆清单

**硬指标**：≥ 3 家；至少包含 1 家头部 SaaS 代表 + 1 家开源/自研代表。本报告覆盖 5 家（SaaS ×2 + 开源 ×3），达标。

| 编号 | 标杆系统 | 厂商 / 社区 | 部署形态 | 场景覆盖 | 技术亮点 | 商业模式 | 调研来源 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| B1 | Feedly | Feedly Inc. | SaaS（仅云端） | RSS 聚合 + AI 内容情报（Leo AI）+ 团队看板 | Leo AI 优先排序/去重/摘要；Zapier/IFTTT 集成 | 免费增值订阅（Pro $6.99/月，Pro+ $12.99/月，Enterprise $1,600/月起） | SR-06, SR-08 |
| B2 | Inoreader | Innologica Ltd. | SaaS（仅云端） | RSS 聚合 + 监控源 + 自动化规则 + 社交源 | 规则/过滤器引擎（30 规则/50 过滤）；Intelligence AI（1M tokens/月）；Web feeds（无 RSS 站点监控） | 免费增值订阅（Free 150 源；Pro $7.50/月年付；Team $44.99/月起） | SR-07, SR-08 |
| B3 | Miniflux | 开源社区（Frédéric Guillot 主导） | 自托管（单二进制 / Docker） | 极简个人/小团队 RSS 阅读 | Go 静态单二进制；仅 PostgreSQL；Fever + Google Reader API + REST API；内置 Readability 全文抓取 | 开源免费（Apache-2.0） | SR-01, SR-02, SR-09 |
| B4 | FreshRSS | 开源社区（100+ 贡献者） | 自托管（LAMP/LEMP / Docker） | 功能完整的多用户 RSS 聚合器 | Google Reader API + Fever + 原生 API；WebSub 实时推送；50+ 扩展 + 主题；XPath 网页抓取生成 Feed | 开源免费（AGPL-3.0） | SR-03, SR-04, SR-09 |

### 2.2 标杆方案详述

#### 2.2.1 B1 - Feedly

| 维度 | 内容 | 置信度 |
| --- | --- | --- |
| 产品定位 | 面向个人知识工作者与企业情报团队的云端 RSS/内容情报平台 | 已核实（SR-06 官网） |
| 目标用户 | 内容营销者、研究者、市场/威胁情报团队 | 已核实（SR-06, SR-08） |
| 核心能力 | RSS/Newsletter/YouTube 聚合；Leo AI 优先排序、去重、静音过滤、摘要；Boards 收藏与团队共享；全文搜索（付费）；OPML 导入导出 | 已核实（SR-06, SR-08） |
| 架构特点 | 纯云端多租户 SaaS，无私有化选项；AI 能力（Leo）为其核心差异化层，构建于自有内容图谱之上 | 推断（来源：SR-08 定价分层中 AI 仅存在于 Pro+ 以上档位） |
| 部署形态 | SaaS 唯一形态，不支持自托管 | 已核实（SR-06） |
| 集成方式 | Zapier / IFTTT / Slack / Evernote / OneNote / Buffer；Enterprise 档提供 API 访问与 SSO/SAML | 已核实（SR-06） |
| 定价模式 | Free（100 源 / 3 feeds，无搜索无 AI）；Pro $6.99/月（年付 $6/月，1,000 源）；Pro+ $12.99/月（年付 $8.25/月，2,500 源 + Leo AI）；Enterprise $1,600/月起 | 已核实（SR-06, SR-08，2026 年定价） |
| 优势 | AI 驱动的降噪与优先级排序是品类标杆；阅读体验与移动端打磨成熟；OPML 可迁移降低锁定 | 综合归纳（SR-08） |
| 局限 | 免费档 100 源/3 分组上限且带算法干预风险；AI 能力锁定在 Pro+ 以上；数据（阅读行为、标注）存于第三方；无自托管选项 | 已核实 + 推断（SR-06 定价表；隐私与锁定风险为综合归纳） |
| 对本项目的参考价值 | 功能分层（免费/Pro/Pro+）展示了"核心阅读 → 搜索 → AI 降噪"的能力演进路径；其 AI 功能可作为本项目远期（P2+）方向参照，但其 SaaS 形态与本项目自托管诉求根本冲突 | 推断 |

| 维度 | 内容 | 置信度 |
| --- | --- | --- |

| 目标用户 | 重度 RSS 用户、研究员、小型监测团队 | 已核实（SR-07, SR-08） |

| 架构特点 | 云端 SaaS；以"规则 + 过滤 + 监控"自动化引擎为差异化核心；AI 为可插拔增值服务（BYOAI） | 已核实 + 推断（SR-07 功能分层；BYOAI 见 SR-08，2026-04 上线） |
| 部署形态 | SaaS 唯一形态，不支持自托管 | 已核实（SR-07） |

| 优势 | 规则/过滤器自动化是 RSS 品类最完整的实现；免费档 150 源足以覆盖本项目 41 源规模；全局搜索与监控源能力强 | 综合归纳（SR-07, SR-08） |

#### 2.2.3 B3 - Miniflux

| 维度 | 内容 | 置信度 |
| --- | --- | --- |
| 产品定位 | 极简主义、主见明确（opinionated）的自托管 Feed 阅读器，"少即是多" | 已核实（SR-01 官网） |
| 目标用户 | 注重隐私、追求低维护成本的个人自托管用户与小团队 | 已核实（SR-01, SR-09） |
| 核心能力 | RSS 1.0/2.0、Atom 0.3/1.0、JSON Feed 解析；OPML 导入导出；分类 + 书签；内置 Readability 全文抓取 + CSS 选择器抓取规则 + 正则重写/过滤规则；PostgreSQL 全文搜索；Fever + Google Reader API + REST API；多用户；键盘快捷键 | 已核实（SR-01 功能页） |
| 架构特点 | Go 编写的静态编译单二进制，无外部运行时依赖；仅支持 PostgreSQL（刻意设计，不做 SQLite/MySQL）；不使用 ORM 与重型框架；静态资源经 Go embed 打包进二进制；服务端渲染 + 极少 vanilla JS；进程内调度器或 cron 后台抓取；遵循 Twelve-Factor（全部环境变量配置） | 已核实（SR-01 功能页"Technical Stuff"段） |
| 部署形态 | 自托管：单二进制 / Debian/RPM 包 / 官方 Docker 镜像（约 30MB，支持 ARM）；资源占用约 30–80MB RAM（200 源规模实测约 80–120MB 抓取峰值） | 已核实（SR-01；资源数据见 SR-09/SR-10 社区实测） |
| 集成方式 | REST API（官方 Go/Python 客户端库）；Fever 与 Google Reader API 兼容第三方客户端（Reeder、NetNewsWire、FeedMe 等）；25+ 第三方保存/通知集成（Wallabag、Pinboard、Telegram、Matrix 等）；Webhook；OIDC/Passkeys/OAuth2 认证 | 已核实（SR-01） |
| 定价模式 | 开源免费，Apache-2.0 许可 | 已核实（SR-01, SR-02） |
| 优势 | 部署极简（一个二进制 + PostgreSQL）；资源占用极低；隐私设计内建（去追踪参数、媒体代理、无遥测）；代码库小、可维护性高；社区活跃（GitHub 约 9.3–9.5k stars，2026 年持续发版，最新 2.3.1 于 2026-05-29） | 已核实 + 综合归纳（SR-02；star 数与发版记录见 SR-02, SR-09） |
| 局限 | 无插件/扩展系统，主题定制有限；不支持 WebSub 实时推送；Google Reader API 支持为部分实现（不如 FreshRSS 完整）；多用户注册需管理员手工创建 | 已核实（SR-09, SR-10 对比实测） |
| 对本项目的参考价值 | **架构范式首选参照**：单二进制 + 内嵌调度 + 服务端渲染 + 环境变量配置，与"41 源个人自托管"规模高度契合；其隐私处理（去追踪参数、no-referrer）可直接借鉴；其"刻意克制"的功能边界是 MVP 范围控制的范例 | 推断 |

#### 2.2.4 B4 - FreshRSS

| 维度 | 内容 | 置信度 |
| --- | --- | --- |
| 产品定位 | 功能完整、可扩展的自托管 RSS/Atom 聚合器，自托管阵营"功能派"代表 | 已核实（SR-03, SR-04） |
| 目标用户 | 需要多用户、扩展定制、移动客户端生态的自托管用户；家庭/小团队共享实例 | 已核实（SR-04, SR-09） |

| 定价模式 | 开源免费，AGPL-3.0 许可 | 已核实（SR-03） |
| 优势 | 功能覆盖最广的开源方案；SQLite 零依赖起步、可平滑升级 PostgreSQL；WebSub 实时性；客户端 API 生态最完整；社区最大（GitHub 约 15.6–15.8k stars，2026 年持续活跃，最新 1.29.1 于 2026-05-20；近 30 天 star 增长 +213） | 已核实 + 综合归纳（SR-03；star 与活跃度见 SR-03, SR-09） |
| 局限 | PHP + Web 服务器栈相对厚重（内存约为 Miniflux 的 2–3 倍）；抓取调度依赖 cron 配置（最常见的自托管失误点）；AGPL-3.0 对二次开发并对外提供服务的场景有源码公开义务 | 已核实（SR-09, SR-10；AGPL 义务为许可证事实） |
| 对本项目的参考价值 | **功能基线首选参照**：发布频率统计、死源检测扩展直接回应 material_digest 中"已失效"分组的痛点；WebSub 支持展示了推送式更新路径；SQLite 起步的数据库策略与 41 源规模契合；若本项目选 PHP 技术栈，其架构可直接对标 | 推断 |

### 3.2 评分结论

> 基于 §3.1 加权总分，形成分层结论。每层结论必须引用得分作为依据。**本结论为调研侧建议，非冻结决策，最终边界由 business-architect 裁决。**

- **优先借鉴**：**B3 Miniflux** — 适用度评分：**5.00**。理由：场景契合度满分（自托管、个人规模、Web 形态完全一致）；其**架构理念**（单二进制分发、单一数据库、进程内调度、环境变量配置、功能克制）仍可作为本项目系统设计参照；Apache-2.0 许可对源码研读与思想迁移零约束；隐私处理内建。注：经 G2 用户反馈确认技术栈为 Rust + 前后端分离后，其具体技术实现（Go 语言、服务端渲染）不再作为本项目直接参照，借鉴范围收敛为架构理念层面（见 §4.3）。
- **优先借鉴**：**B4 FreshRSS** — 适用度评分：**4.65**。理由：功能基线最完整（发布频率统计、死源检测、WebSub、Google Reader API 生态），直接回应 material_digest 中"已失效"源痛点；SQLite 起步策略与 41 源规模契合。扣分点在技术栈厚重与 AGPL 约束——若本项目不修改其源码而仅借鉴设计，则 AGPL 不构成实际障碍。
- **部分借鉴**：**B5 Tiny Tiny RSS** — 借鉴点：文章过滤/去重/标签的功能模型、独立 updater 进程的调度设计。不借鉴的部分：多容器部署形态（对个人规模过重）、其社区生态模式。理由：总分 3.55，功能成熟但部署哲学与生态活跃度不符合本项目。
- **部分借鉴**：**B2 Inoreader** — 借鉴点：规则引擎（条件→动作）与过滤器模型（P1/P2 功能参照）、自动 OPML 备份、Web feeds 概念（无 RSS 站点监控）。不借鉴的部分：SaaS 形态与订阅模式。理由：总分 2.75，场景契合度仅 2 分（闭源 SaaS），但功能设计有明确参考价值。
- **不借鉴（否决）**：**B1 Feedly** — 否决理由：场景契合度 2 分，纯 SaaS 与自托管诉求根本冲突；核心差异化能力（Leo AI）锁定在 $12.99/月以上档位且依赖其云端内容图谱，技术上不可迁移到自研自托管项目；总分 2.60 为五家最低。其功能分层思路（核心阅读→搜索→AI）仅作为远期路线图概念参照，不进入借鉴清单。

### 4.3 技术栈参考建议

> **「经 G2 用户反馈确认」**：本节技术栈方向（Rust 后端 + SQLite + 前后端分离 + 单一可执行文件/单容器部署）为 G2 人工审核中用户的显式决策，用户原文：「技术栈方面，我希望使用rust作为后端语言，数据库使用sqlite，前后端分离，部署需要适配单一可执行文件和单容器」。该决策视同冻结，下游 system-architect 不得再就后端语言 / 数据库 / 前端形态 / 部署形态发起同论题中间确认；本节中框架与库级选型仍为调研侧建议。

| 技术层 | 推荐方案 | 替代方案 | 选择理由 |
| --- | --- | --- | --- |
| 后端语言/框架 | Rust（Axum，Tokio 生态） | Actix-web（同为成熟 Rust 框架，SR-14） | 「经 G2 用户反馈确认」。Rust 编译为静态单二进制，与"单一可执行文件"部署诉求天然契合；无 GC、内存安全、资源占用低（B3 以 Go 实测 30–80MB RAM，Rust 同量级或更低）；Axum 为 Tokio 官方生态主流 Web 框架，社区与文档成熟。客观提示：Rust 学习曲线与编译时长相较 Go/PHP 更陡，若开发者主语言非 Rust，初期开发节奏会放缓，此为已知的切换成本 |
| 数据库 | SQLite（FTS5 全文搜索） | PostgreSQL | 「经 G2 用户反馈确认」，维持原推荐。41 源单用户规模下零运维、单文件备份；B4 以 SQLite 为默认选项证明该规模可行性；若 §5.2 U-01 未来确认为多用户方向，再评估迁移 PostgreSQL |
| Feed 解析库 | feed-rs（Rust，MIT） | rss + atom_syndication crate 组合 | feed-rs 提供统一数据模型，覆盖 RSS 0.x/1.0/2.0、Atom、JSON Feed，支持 iTunes / Dublin Core / Media RSS 扩展与 sanitize 特性；crates.io 月下载约 17 万次、被 52 个 crate 依赖，v2.4.0（2026-07）持续维护（SR-11）；解析策略宽松（lenient），对非规范 Feed 容错较好，可覆盖 material_digest 中 rss/atom/rss2/feedburner 等全部路径形态 |
| 全文抓取 | readabilityrs（Rust，Apache-2.0，Mozilla Readability.js 的 Rust 移植） | 经 Node 侧车调用 Readability.js 原库（不推荐，引入额外运行时） | B3 内置 Readability 证明该能力对个人阅读器必要；readabilityrs 通过 Mozilla 官方测试套件 119+/130 用例，支持输出清理后 HTML 与 Markdown（SR-12）；注意其为 0.1.x 年轻库，成熟度风险见 §5.1 R-06 |
| 前端 | 前后端分离 SPA（Vue 或 React 任选其一） | 服务端渲染 + 渐进增强（对标 B3，未采纳） | 「经 G2 用户反馈确认」。如实标注：前后端分离与 B3 的 SSR 范式不同，此为用户显式决策而非调研推荐结论。后端提供 REST API，前端独立构建；前端构建产物可经 rust-embed 在编译期嵌入 Rust 二进制（SR-13），从而同时满足"前后端分离"与"单一可执行文件"两项约束 |
| 抓取调度 | 进程内调度器（Tokio 异步任务，逐源独立间隔 + 指数退避） | 系统 cron + 脚本 | B3 进程内模式使部署保持单组件，与单一可执行文件目标一致；退避策略应对失效源（material_digest 已有失效先例） |
| 部署形态 | 单一可执行文件 / 单容器 Docker（含 SQLite） | 多容器编排 | 「经 G2 用户反馈确认」，维持原推荐。与 B3 一致的"拷贝即用"体验；B5 的多容器形态已被 §3.2 证明不适合本规模；rust-embed 使前端资源无需独立静态文件服务（SR-13） |
| OPML 处理 | quick-xml / serde（Rust 生态） | — | OPML 1.0 结构简单；feed-rs 底层即基于 quick-xml（SR-11），依赖可复用 |
